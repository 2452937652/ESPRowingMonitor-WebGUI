# 2026-09-26 会话指标缺失检查

## 结论与范围

本次已确认 Web UI 存在指标被覆盖、历史记录选取不一致和设置读取时序问题。修复位于本 WebGUI 仓库，不需要重新烧录固件。没有修改机器参数、NVS 或固件，也没有进行真机蓝牙验收；不能据此断言固件所有功能均无问题。

对照了官方 WebGUI v7.2.0 源码、当前个人版本、线上发布的 JS/Service Worker 文件和用户提供的 CSV、JSON、FIT。部分旧数据处理逻辑也来自官方版本，因此不能把每一项都归因于个人修改。

## 数据证据

- 两份 JSON 内容相同，共 848 条记录、103 桨；每条记录都有非零恢复时间。
- 466 条记录的桨频和每桨距离为 0。103 桨的最后一条记录全部为 0，但其中 102 桨较早的记录保存了非零值。
- 同一桨的飞轮通知仍会继续到达。旧算法用相邻通知计算桨频和每桨距离，未增加桨数时产生 0，随后覆盖已算出的值。历史汇总取最后记录，CSV 曾取较早记录，造成不同页面/导出表现不一致。
- FIT 完整性检查通过，记录 103 桨、808.59 米，与 JSON 一致。文件损坏不是本次现象的解释。
- 103 组历史力曲线的 driveLength 全部为 0。旧图表把采样序号当作距离，产生了截图中的异常厘米刻度。原文件没有可靠的物理长度，不能精确补出。
- 原导出把同一桨的多次更新重复计入总做功。记录中的总做功不能当作可靠能量结果。

## 修复

1. 桨频和每桨距离按完整的桨边界计算；飞轮更新继续更新速度，停止状态允许桨频归零。
2. 历史分析和 CSV 共用逐桨记录选取逻辑，保留旧记录中已有的有效桨频、距离和拉桨时间。原始记录不会被重写，也不凭空恢复第一桨或缺失长度。
3. 新协议需要的两个特征均存在时才启用；部分可用时走完整旧协议路径，避免等待永远不会收到的数据。
4. 实时页等待本桨恢复数据时显示最近已完成的恢复指标；晚到数据仍保存到所属桨，显示用数据与持久化数据分开。
5. 设置读取失败后真正重新读取；设置晚到也能重新计算旧协议拉桨长度。
6. 未知物理长度的历史曲线使用采样点横轴。总做功按逻辑桨去重，重复更新替换同一桨贡献。
7. 兼容导入旧 v4 数据库；仅允许已知的 v4 到 v5 路径。

旧记录可以恢复“原来保存过但被显示逻辑遗漏”的数值，但这些旧数值本身仍可能受原计算算法影响，不等同于重新测量。恢复时间实时缺失涉及的协议/时序路径已有回归覆盖，仍需上线后通过实际设备确认。
